# Hardware diagnostics and numerical checks

These optional tools exercise hardware interfaces or analyze explicit input captures. They are reference tools rather than an application suite. Inputs, hardware access and any required applied kernel tree are supplied by the caller. No private capture data is included.

- `hardware-proofs/iep-721/` generates synthetic format, colour, field-order, impulse and coefficient-basis cases. Its `exercise.c` includes the public `tools/iep-test.c`. Python generators/analyzers use NumPy; plots also need Matplotlib. Build the exerciser with `cc -O2 exercise.c -lm -o exercise` from its directory.
- `hardware-proofs/iep-620/` retains an earlier IEP test interface and read-only register snapshot utility. The latter refuses access unless the IEP reports active runtime power. This historical utility is specific to the RK3128 address map; it does not acquire ownership of an active driver.
- `hardware-proofs/rga1/` checks captured bit-packing, lookup-table and dithering results. Scripts receive a capture directory; those files are not shipped. These independent pixel checks document both supported operations and refused combinations.
- `hardware-proofs/fixtures/` generates synthetic image fixtures and compares pixel/filter/conversion results. NumPy and Pillow are required. No photographs are included.
- `hardware-proofs/touch/` contains a deterministic Silead contact/history corpus, a point-helper test and a gesture test model. `bash research-tools/hardware-proofs/touch/point-sim.sh` extracts the actual helper additions from the two public touchscreen patches and checks the finite corpus. The optional independent ARM oracle requires a caller-supplied image and Unicorn; it is unnecessary for normal finite validation.
- `hardware-proofs/host/` contains deterministic RGA callback/MMU/IRQ/allocation test generators and Lima/SSV ownership models. RGA Python generators take an applied driver source path and output a C test; compile it with the applied driver's headers plus `tools/rga1-controls.h`. `lima-timeout-sim.py APPLIED_KERNEL` compiles the actual Lima recovery functions with controlled host API mocks. `bash research-tools/hardware-proofs/host/ssv-scan-sim.sh` tests the published SSV source without RF or root access. `iep_controls_kunit.c` is a KUnit template requiring an `iep-control-under-test.h` generated from the applied IEP control callbacks.
- `hardware-proofs/gpu/` contains a GL framebuffer hash interceptor, a presentation-pipeline simulator and a trace-event numerical parser. Build `framehash.c` as a shared object with EGL/GLES2 headers and `-fPIC -shared -ldl`. It reads pixels before swap and changes workload cost, so hashes and timing have different purposes. `pipesim.py` accepts a JSON event record. The trace parser accepts a tracefs text capture around an explicit finite workload.
- `hardware-proofs/input/touchinj.c` is an explicit historical evdev injector. It requires the device path and caller-selected coordinates; it is not an input service.
- `malitrace/` contains historical graphics diagnostic capture, binary decoding and shader compiler tools. `limaparse.c` additionally requires Mesa's generated `lima_pack.h`. The GL capture helper requires EGL/GLES2, zlib, pthread and libdl.
- `experiments/` contains historical patches outside the accepted default series. See its status notes before using any of them.

The fixture tools use synthetic data. Private operation runners, association-control scripts tied to particular access points, deployment scripts and application-dependent benchmarks are omitted. The published Wi-Fi capture analyzer takes its input directory and expected BSSIDs explicitly. Driver code and hardware checks retain their individual license notices.
